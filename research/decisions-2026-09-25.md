## 並列・複数モデル

| # | 論点 | 決定 |
|---|---|---|
| Q5 | 並列の既定形 | **課題の性質で自動選択**。設計に複数の正解があれば arena（同じ課題を N モデルで競わせて選ぶ）、独立スライスに分けられれば swarm（分割して N worker）。入口 skill が判定規則を持つ |
| Q6 | モデル構成 | **実装＝Claude、判定＝別系統必須**。worker は Claude（opus / sonnet）、judge・レビューは Codex を必ず 1 本含める。「書いた者と判定する者を別系統に」を不変条件にする |
| Q7 | 作業空間 | **1 worker ＝ 1 worktree 必須**（書き込む worker）。読み取り専用（調査・judge）は共有でよい |
| Q8 | 人間の checkpoint | **判定器の合意と不可逆操作のみ**。「何をもって完了とするか」の合意と、スキーマ変更・公開・送信などの不可逆操作だけ止まる。それ以外は実験で決めて進む |
| Q13 | hearing を入れる閾値 | **不可逆な変更、または worker を 2 以上 fan-out するとき**。並列は仕様の曖昧さが N 倍になるので、そこだけ先に詰める |

## TDD モード

| # | 論点 | 決定 |
|---|---|---|
| Q9 | 原則 TDD の例外 | **例外を明文化し、代わりに verify を要求**。config・配線・glue・型注釈はユニットテスト免除。ただし「判定器なし」は認めず、verify スクリプトや型チェックを判定器にする |
| Q10 | refactor の位置 | **スライス完了後に別エージェントが担当**。red-green を N スライス回した後、実装と別のエージェントが refactor し、全テスト再実行で green を確認する |
| Q11 | カバレッジ 80% | **品質基準を優先、数値は目安に降格**。undefined テスト・禁止 5 形・tautological 禁止をゲートにし、80% は「下回ったら理由を書く」目安にする |
| Q12 | seam の事前合意 | **取り込む。Q8 の「判定器の合意」と同一視**。seam 候補には「何を捕まえ何を見逃すか、実行時間」を併記する |
| Q14 | red の機械的確認 | **入れる。テスト実行ログを証拠ファイルに残す**。red と green の実行出力をスクリプト経由で証拠ファイルに記録し、完了報告はそのファイルを参照。チェックスクリプトや pre-commit が検査できる形にする |

## 決定から導かれる不変条件（設計時に守るもの）

1. 判定器なしに実装を始めない。判定器が無い場合は、判定器を作ることが最初のタスク
2. 判定器そのものを先に検証する（red になるべき入力で red になるか）
3. 書いた者と判定する者は別系統のモデル
4. 書き込む worker は専用 worktree
5. 完了報告は証拠ファイルを参照する。自己申告のみの完了は無効
6. 人間を止めるのは、判定器の合意と不可逆操作のとき、および fan-out 前の hearing のみ
7. 規律は指示文より構造（スクリプト・チェック）で強制する
8. サブエージェントの brief には「直接実行し、スキル呼び出しや追加のエージェント起動をしない」を必ず入れる
