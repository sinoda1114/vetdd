# vetdd 実装計画（2026-09-25）

前提: `decisions-2026-09-25.md` の 19 決定と 8 不変条件。この計画は未決 6 点を決め、ディレクトリ構成と実装順に落とす。

## 1. 要件の再確認

vetdd は Claude Code 用の skill 群で、次を提供する。

1. **共通骨格**: 判定器を先に作る → 判定器を検証する → red → green → 実物で証明。入口 skill `/vetdd` が課題を読み、モード（test / verify / eval）と並列形（single / arena / swarm）を選ぶ
2. **test モード**: 合意した seam に red テスト → 最小実装で green → スライス完了後に別エージェントが refactor → 全テスト green。red / green の実行ログを証拠ファイルに残す
3. **verify モード**: プロジェクトごとに verify skill（Launch / Doctor / Drive / Evidence / Cleanup と feature map）を生成し、1 周回して証拠が残ることを確認してから納品する。config・配線・glue など test 免除の変更はこのモードが判定器になる
4. **eval モード**: skill / prompt の変更をブラインド A/B で評価する。candidate は Claude、judge は Codex。結果は回帰セットとして貯まる
5. **並列**: 書き込む worker は 1 worktree、判定は別系統、fan-out 前に hearing、brief に再委譲禁止
6. **配布**: 英語 SKILL.md、日本語 README、MIT、`~/.claude/skills/` へコピー。ドッグフーディングは vetdd 自身

## 2. 未決 6 点の決定

### 2.1 評価結果の永続形式

```
evals/
  index.tsv                      # 追記のみ: ts, eval_id, run_id, variant_a, variant_b, winner, delta, judge_family
  <eval-id>/
    task.md                      # candidate に渡す自然な依頼文（禁止語なし）
    rubric.md                    # judge 専用。3〜6 基準、各基準に 0/1/2 の採点定義
    fixture.md                   # 作業ディレクトリの作り方（fixture の指定、配置する variant）
    runs/<run-id>/               # run-id = YYYYMMDD-HHMM
      candidates/<label>/        # label は c1, c2 …（モデル名を含めない）
        transcript.jsonl         # Claude Code の transcript をコピー
        output/                  # 成果物
      judge.json                 # schemas/verdict.schema.json に準拠
      synthesis.md               # 親の所見、judge との一致・不一致、promote の推奨
```

- 回帰: skill 変更時に `evals/*/` を全部再実行し、`index.tsv` の直近 winner と比較する。baseline の run-id は `evals/<eval-id>/baseline` ファイルに書く
- `verdict.schema.json`: `{ eval_id, run_id, criteria: [{ name, scores: { c1: 0|1|2, … }, note }], winner, confidence: low|mid|high, disagreements: [] }`
- 「同じ結果の再現」ではなく「同じ手順の再現」を目的にするので、transcript を必ず残す（マットさんの "run the document, not debate" の実装）

### 2.2 arena / swarm の自動選択規則

入口 skill が、判定器の合意（Q8）の直後に 2 問を自問し、結果を todo に `parallel: <形> because <理由>` と書く。

| 成果物は 1 つに収束すべき設計か | 互いに独立な slice に分割でき、各 slice が自分の判定器を持てるか | 形 |
|---|---|---|
| no | no | **single**（worker 1、判定 1） |
| yes | no | **arena**（runner N=3 が同じ課題、judge が選ぶ、親が graft） |
| no | yes | **swarm**（slice ごとに worker、各 worker が red → green、親が直列統合） |
| yes | yes | **arena → swarm**（先に設計を arena で選び、その設計を slice に割って swarm） |

- 「収束すべき設計か」の判定: 型・モジュール境界・データ構造を新しく決める変更なら yes。既存の形に沿う追加なら no
- 「独立な slice か」の判定: slice 同士が同じファイルを書かない、かつ各 slice が単独で red テストを書ける。どちらかが崩れたら single に落とす
- worker ≥ 2 の時点で hearing を挟む（Q13）
- arena の runner は Claude 系 3 種（opus / fable / sonnet）、judge は Codex（Q6）。runner の系統が偏るリスクは 5 節に記す

### 2.3 Codex を judge として呼ぶ手段

`scripts/judge.sh` に集約する。呼び出し側は rubric と candidate のパスを渡すだけにする。

```
judge.sh --rubric <rubric.md> --candidates <dir> --out <judge.json> [--model gpt-6-sol] [--effort high]
```

内部:

```
codex exec -s read-only -C <candidates-dir> \
  -m "$MODEL" -c model_reasoning_effort="\"$EFFORT\"" \
  --output-schema schemas/verdict.schema.json \
  -o "$OUT" < <(render judge-prompt.md + rubric)
```

- `-s read-only` で candidate を書き換えさせない
- モデル名・variant 名は prompt に入れない（ブラインド）。label は c1, c2
- 出力は schema で強制し、`check-verdict.sh` が「全 criteria に全 label の score があるか」を検査する
- 既定モデル `gpt-6-sol` / effort `high`。`--model` で差し替え可。`gpt-6-astra` を 2 本目にする `--deep` は後回し
- 認証は `codex login` 済みを前提。未ログインは judge.sh が先頭で検出して止まる

### 2.4 証拠ファイルの形式と検査

```
.vetdd/
  evidence/<slice-id>/
    red.log          # テスト実行の stdout+stderr
    green.log
    refactor.log     # 全テスト再実行（refactor 後）
    meta.json        # schemas/evidence.schema.json に準拠
```

- `meta.json`: `{ slice_id, seam, test_files: [{ path, sha256 }], phases: { red: { cmd, exit_code, started_at, ended_at }, green: {…}, refactor: {…} }, head_sha }`
- 記録は `scripts/evidence.sh <slice-id> <phase> -- <test command>` で行う。tee でログを取り、exit code と時刻を meta.json に追記する。**red は exit ≠ 0、green / refactor は exit = 0 でなければその場で失敗**にする
- 検査は `scripts/check-evidence.sh [<slice-id>…]`。規則は 4 つ: (1) red が green より前、(2) red の exit ≠ 0、(3) green と refactor の exit = 0、(4) test_files の sha256 が現在のファイルと一致（green 後にテストを書き換えていない）
- pre-commit: `scripts/hooks/pre-commit` を `setup-project.sh` がプロジェクトの `.git/hooks/pre-commit` に置く（global hooksPath は触らない）。staged なテストファイルに対応する slice の証拠を `check-evidence.sh` で検査し、無ければ `VETDD_BYPASS=1` が無い限り止める
- `.vetdd/` は既定で gitignore。監査証跡が要るときだけ `--keep` で commit する（pstack の show-me-your-work と同じ方針）

### 2.5 同梱 fixture の中身

`fixtures/ts-kata/`。3 モードすべての練習台になる最小の TS プロジェクト。

- 構成: npm、TypeScript、vitest、`.npmrc`（`ignore-scripts=true` / `audit-level=high` / `save-exact=true`）、`package-lock.json` をコミット
- 題材: 「請求書の締め日・支払期日計算」の小さなドメイン（`src/dueDate.ts`、`src/invoice.ts`、`src/cli.ts`）。理由は、月末・うるう年・営業日という独立した真実の源（暦）があり、tautological テストが書きにくいこと
- 仕込み: (a) 意図的なバグ 1 つ（2 月末の締め日で翌月を誤る）、(b) 未実装の機能 1 つ（土日を営業日に繰り越す）、(c) CLI surface（`npx tsx src/cli.ts due 2026-02-15`）。(a) は test モードのバグ修正練習、(b) は feature の red → green 練習、(c) は verify モードの Drive 対象
- eval モードの task は「(b) を実装せよ」を自然な依頼文にしたもの

### 2.6 skill 間参照の書き方

- 別 skill の起動: `Call the Skill tool with "vetdd"` の形（マットさんの invocation.md 方式）。Claude Code の Skill tool 名を明示する方が発火が安定する
- 同一 skill 内のファイル: `Read references/<file>.md` の相対パス（pstack の "Delegate by path. Don't restate." 方式）
- 原則の引用: `principles.md` の見出し名を太字で書く（例: **prove-it-works**）。引用できるのは起動時に principles.md を読んだ後だけ
- サブエージェントへの brief: `references/subagent-brief.md` のテンプレートを必ず使う。テンプレートの冒頭に「このタスクを直接実行し、Skill の呼び出しや追加エージェントの起動をしない」を固定文で置く

## 5. 依存とリスク

| 深刻度 | リスク | 対処 |
|---|---|---|
| 高 | Codex judge の呼び出しが sandbox や認証で止まる | Phase 4 の bats で未ログイン検出を先に作る。`ai-review` が同じ経路で動いている事実を頼りにする |
| 高 | 証拠ファイルをエージェント自身が書き換える | sha256 と時刻の整合検査、`evidence.sh` 経由以外の書き込みは check で不正扱い。完全防止は不可能と明記 |
| 中 | arena の runner が Claude 系のみで発散が弱い | Phase 6 で観測し、弱ければ Codex を runner に加える（Q6 の「実装＝Claude」の見直し候補として記録） |
| 中 | principles.md の常時読み込みが context を圧迫 | 10 原則・各 3 行以内・合計 80 行以内を上限にする |
| 中 | サブエージェントの再帰増殖 | brief テンプレートの固定文と、Phase 3 の transcript 確認 |
| 中 | eval の judge が「採点者に好かれる出力」を選ぶ | rubric を観測可能な基準（テストが通る、証拠ファイルがある）に限定する。印象基準を入れない |
| 低 | fixture の暦計算が題材として重い | 祝日は扱わず、月末・うるう年・土日だけに絞る |

## 6. 複雑度と順序の根拠

- 複雑度: 高。Phase 0〜7、各フェーズが独立した判定器を持つ
- 順序の根拠: 証拠の仕組み（Phase 1）を最初に作るのは、以降の全フェーズがそれを判定器に使うため。eval（Phase 4）を verify（Phase 5）より先にするのは、eval が SKILL.md の改善ループを回す道具であり、早く持つほど後のフェーズの品質が上がるため
- Phase 1 と Phase 2 は独立なので並列可。Phase 5 と Phase 6 も独立。1 worker 1 worktree の規律に従い、並列にする場合は worktree を分ける
