### 摩擦と、この PR での手当て

1. **親が単位のコマンドを打ち間違えた（約 14 秒）。** `integrated` を記録するときに、テストファイル名を `satday.test.ts` と組み立てて赤になりました。記録には accepted=false が 2 件残っています。
   - 手当て: `evidence.sh <slice> integrated --rerun` を足しました。単位の `after` に記録されたコマンドを、もう一度走らせます。swarm.md の統合と Close はこれを使います。
2. **worker のログに worktree のパスが残り、judge-layout が exit 4 で止まった（約 1.5 分）。** ログに `<repo>.vetdd-wt/<slice>` が残り、判定者への検査に当たりました。
   - 手当て: judge-layout.sh が `<root>.vetdd-wt/<slice>` も `<repo>` に置き換えます（テストあり）。
3. **親が Close で既存のテスト一式の `integrated` を飛ばした（判定 partial）。** 全テストと型検査を記録しないまま、返信で緑と書きました。
   - 手当て: swarm.md の Close に「各 slice の自分のコマンド（`--rerun`）と、合意した既存のテスト一式」と明記しました。`--rerun` は、親が `worktree.sh add <slice> -- <コマンド>` で決めたコマンドだけを使います（レビューの第 2 周で、worker の記録から拾う作りをやめました）。
4. **返信の主張に根拠を示していなかった（判定 partial）。** 「第 3 引数なしでは今と同じ」を実測と書いたのに、根拠の記録を示していませんでした。親の書き方の問題で、判定者が正しく見抜きました。

### 気づいたこと

- worker の指示書の「Report」に、開始と終了の時刻を入れると、親の記録と突き合わせられます。今回は手で入れました。
- calibrate.sh は、校正の状態を `.git/worktrees/<slice>/vetdd-calib/` に置きます。worktree を消すと一緒に消えるので、問題はありません。

### レビューで決めた線（脅威モデル）

/ai-review の第 2・3 周で、own-security が「worker が悪意を持つ、または乗っ取られる」前提の経路を次々に挙げました。
- worker の書いたコマンドを親が実行する
- 偽の `.git`
- リンク
- 追跡させた `.vetdd/` ファイル
- 共有の git 設定

worker は親と同じ OS ユーザーで動くので、本気で悪意があれば、メインのリポジトリやホームを直接書けます。この方向を突き詰めると収束しません（2026-10-03 の反省、9 回回しても収束しなかった件と同じ形）。

そこで swarm.md に「What it protects」を書き、守る範囲を「親が自分の手順の中で、worker の書いたものを実行したり取り込んだりする経路」に限りました。具体的には次のとおりです。
- `--rerun` は、親が `add` で決めたコマンドだけを走らせます。記録は作業木の外の git ディレクトリに置きます。
- git は、メイン側が持つ管理ディレクトリを通して、hooks と fsmonitor を切って動かします。
- リンクは取り込みません。
- merge の前に `worktree.sh check` で、ブランチの中身と共有の git 設定を確かめます。

この線の外の残りは Issue に回しました。

- 親は判定器（`src/rollover.test.ts`、KATA の 3 例と第 3 引数なしの場合）を先に書き、赤を確かめてからコミットしました。
- 走者: l1 = opus、l2 = fable、l3 = sonnet（`models.sh arena-runner` の順）。3 人を裏で同時に動かしました。
- 結果:

### 摩擦と手当て

1. **判定者に、どの案も check-evidence の FAIL として見えた（1 回目の判定が無効）。** ゲートは `--before-close` 付きで緑と判断したのに、judge-layout は付けずに走らせ直していました。そのため、変異テストがまだ無いことが規則 10c の FAIL として見えていました。
   - 手当て: judge-layout に `--before-close` を足し、arena-layout から渡すようにしました（テストあり）。
2. **走者が「実測」と書いた全テストと型検査に、根拠の記録が無かった。**
   - 手当て: 走者の指示書で、全テストと型検査も evidence.sh で記録させるようにしました。
3. **親が変異テストの範囲に、変えていない行まで含めた。** その結果、古いコードで 2 つの mutant が生き残りました。変えた行だけで取り直して OK になりました。
4. **最終判定が fail。**
   - 原因の 1 つ目は、3 人全員が合意にない「未知のモードは RangeError」を足していたことです。arena の判定者は 1 点、最終判定者は 0 点を付けました。
   - 手当て: 走者の指示書に「合意にない振る舞い（防御のための検査も含む）を足さない」と書きました。
   - 原因の 2 つ目は、親が手元にしかない合成の記録を「実測」と引いたことです。arena.md に、手元のファイルは推測（inferred）として引くと書きました。
