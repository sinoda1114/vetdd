# IDS の工夫を取り入れる計画（2026-10-03）

材料: Agarwal et al., "Inductive Deductive Synthesis: Enabling AI to Generate Formally Verified Systems", arXiv:2605.23109。解説スライド「証明しながら実装するエージェント」（数理の弾丸）。第三者レビュー（Claude Fable 5.1 と GPT-6-Astra の突合、ローカルの `.3rd-review/run-top-20261003-112728/report.md`）。

## 方針

- 定理証明器（Rocq / Lean）を vetdd の中心には入れない。想定する利用者のプロジェクトには導入の費用が大きく、LLM が書く形式仕様は空疎になりやすい
- IDS の段取りの工夫を取り入れる: 仕様を途中で変えさせない、やり残し（`Admitted`）の数を進捗にする、行き詰まったら設計から作り直す、監査で空疎な証明を落とす

## 篠田さんの決定

| 項目 | 決定 |
|---|---|
| 範囲 | 改訂案 1〜5 を全部（6 も含む）。5 は Phase 6 と一緒に作る |
| 最優先 | 判定器のこっそり書き換えの検査（check-evidence 規則 8） |
| 追加の検査の予算 | 変更の大小に関係なく毎回しっかり。変異テストの道具があれば毎回使う。欠陥を植える対象が無いモード（verify、eval）はできる範囲 |
| 欠陥を植える係 | 道具（Stryker など）を優先。無ければ原則 1a の合意で決める |
| 記録の形の変更 | S1（判定器の版の理由と再合意）、S2（テストの件数）、S3（監査の結果）を承認。S4（作り直しの記録）は Phase 6 の時点で改めて承認を得る |
| 共有テストファイル | 作業（slice）ごとにテストファイルを分けるよう勧める。共有したときは、規則 8 どおり版の更新と再校正を求める |
| ts-kata への Stryker | 入れる（版を固定、devDependencies）。通常のテストは取っておいた報告を使い、実物の Stryker は指定したときだけ |
| 空のテスト（全 import を undefined にしても通る） | 不合格にする。最終判定の rubric の同じ判定は外して二重にしない |
