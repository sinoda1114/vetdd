# vetdd

**V**erification / **E**val / **T**est **D**riven **D**evelopment。Claude Code 用の skill です。

AI でコードを書く速さは上がりました。同じ速さで、動かないコード、実装をなぞるだけのテスト、「できました」という自己申告も増えます。vetdd は、**判定器を先に作り、判定器で証明が済むまで完了と呼ばない**ための道具です。

## なぜ vetdd か

エージェントに仕事を任せたとき、いちばん困るのは「終わったと言うが、本当に終わったのか分からない」ことです。原因は 3 つに分かれます。

1. **何をもって完了とするかが決まっていない。** テストも検証手順も無いまま書き始め、最後に「動きました」と言われます
2. **判定器があっても、判定器自体が壊れている。** 通るように書かれたテスト、実装と同じ計算で期待値を出すテスト、一度も赤くなったことのないテストです
3. **書いた本人が採点している。** 同じ文脈が自分の成果物を見直しても、確認バイアスの追認にしかなりません

vetdd はこの 3 つに、1 つの骨格で答えます。

```
判定器に合意する → 判定器を作り、校正する（既知の正常例で緑、狙った欠陥で赤）
→ 変更前を測る → 変更する → 変更後を、統合したツリーで測る
```

バグ修正や機能追加では「変更前」が製品上の赤で、「変更後」が緑です。振る舞いを変えない変更（refactor・設定・配線）では校正の赤がその代わりになり、変更前後の両方が緑であることを確かめます。判定器の種類が変わるだけで、骨格は同じです。

| モード | 判定器 | 使う場面 |
|---|---|---|
| **test** | 失敗するテスト | 関数・モジュールの追加や修正 |
| **verify** | アプリを実際に操作する検証スクリプト | 機能全体の確認、テストを免除する変更（設定・配線・glue）の判定 |
| **eval** | 別系統のモデルによるブラインド採点 | skill や prompt の変更が振る舞いをどう変えたか |

## 並列と別系統の判定

vetdd は並列を前提にしています。ただし条件付きです。

- **書く者と採点する者は別系統のモデル。** 実装は Claude、判定は Codex を必ず 1 本含めます。判定者に渡すのは出所やモデル名を伏せた成果物と証拠です。判定の一致・不一致はそのまま結論にせず、同じ成果物を同じ条件で見たかを確かめてから、基準を直すか `inconclusive` で止めるかを決めます
- **書き込む worker は 1 人 1 worktree。** 同じ checkout を 2 人で触る事故（commit の混線、stash の共有）を構造で防ぎます
- **並列の形は 2 つで、条件が違います。** arena（同じ課題を複数モデルで競わせて選ぶ）は契約と判定器を共有し、書き込み先と可変な実行資源だけを隔離します。swarm（独立した slice に分けて同時に進める）はそれに加えて、slice 同士が別のファイルを触り、他の slice が依存する契約を変えないことが条件です。どちらも満たさなければ単独で進めます。完了の判定は worker の個別成果ではなく、親が共通の基点から統合したツリーに対して行います
- **worker を 2 人以上立てる前には、要件を人と詰めます。** 仕様の曖昧さは並列にすると N 倍になるからです

仕事は、判定器の合意で決めた範囲・環境・予算の中で自律的に進めます。人を止めるのは「判定器の合意」「合意に含まれていない操作で、効果が作業空間の外に及ぶか元に戻せないもの（本番の状態、外部への送信や公開、バックアップの無いデータ）の前」「worker を 2 人以上に分ける前」の 3 点だけです。それ以外は実験で決めて進み、結果を見せて、後から直してもらいます。進めなくなったとき（必要な判定者が使えない、環境に届かない、判定器が安定しない）は、証拠を添えて `blocked` か `inconclusive` で止まります。証拠の無い「完了」は出しません。

## 証拠は自己申告ではなくファイル

判定器の実行ログは `scripts/evidence.sh` を通して `.vetdd/evidence/` に残ります。完了報告はそのファイルを参照します。証拠には種別（校正 / 変更前 / 変更後 / 統合後）があり、それぞれ実行したときのツリー（コミットと未コミット差分）・判定器の版・実行条件に結び付きます。変更前の red は、製品を変えた後も履歴として有効です。納品するツリーの裏付けになるのは、そのツリーと一致する最終の「変更後」か「統合後」の証拠だけです。`scripts/check-evidence.sh` が検出するのは、証拠が無い、red が `target_failure` でない（exit 0、または環境エラー）、変更前と変更後の順序が逆、最終証拠のツリーが納品ツリーと違う、の 4 つです。それ以外（判定器が要件を覆っているか、実行条件が合意した環境と合っているか）は検出できないので、判定器の合意で人が確かめます。規律は指示文ではなく構造で強制する、という考え方です。

## 構成

```
skills/vetdd/
  SKILL.md          入口。課題を読み、モードと並列形を選ぶ
  principles.md     10 原則。入口が起動時に全文読む
  modes/            test / verify / eval
  parallel/         select / arena / swarm
  references/       テストの品質基準、判定器の作り方、brief のテンプレートなど
  scripts/          evidence.sh、check-evidence.sh、judge.sh、setup-project.sh
  schemas/          verdict と evidence の JSON Schema
fixtures/ts-kata/   練習台。請求書の締め日・支払期日計算
evals/              eval の課題・rubric・実行結果（回帰セット）
```

## 導入

```bash
cp -r skills/vetdd ~/.claude/skills/vetdd
```

対象プロジェクトで `scripts/setup-project.sh` を実行すると、`.vetdd/` の作成、`.gitignore` への追記、プロジェクトローカルの pre-commit フックの設置を行います。global の hooks は触りません。

## 由来

vetdd は 2 つの先行作を読み（2026-09-25 時点、pstack v0.15.5 と mattpocock/skills plugin 1.2.3）、共通する部分を土台にしたものです。

- [pstack](https://github.com/cursor/plugins/tree/main/pstack)（poteto）: 「完了は実物の証拠で示す」「second opinion は同じ prompt を別モデルへ」「規律は構造で強制する」。並列と複数モデルの考え方はここから来ています
- [mattpocock/skills](https://github.com/mattpocock/skills)（Matt Pocock）: 「red になる 1 コマンドを示すまで仮説に進まない」「テストは事前に合意した seam にだけ置く」「期待値は独立した真実の源から」。判定器を先に作る規律はここから来ています

vetdd が独自に組み合わせているのは、3 つの駆動を 1 つの骨格で扱うこと、red を見たことをファイルで機械的に確認すること、並列を判定器の独立性と統合後の検証で安全にすることの 3 点です。読んだ範囲では二人の skill にこの組み合わせは無く、比較の根拠は `research/synthesis.md` にあります。
